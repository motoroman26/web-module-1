# Модуль: рефакторинг та аналіз Web API

У репозиторії вже є робочий Orders API на Node.js та Express. Ваше завдання: розібратися в чужому коді, покращити його структуру й не зламати зовнішню поведінку. Орієнтовний час: один тиждень.

## Що ви практикуєте

- обмін HTTP-запитами й відповідями, HTTP-методи та коди стану;
- API-контракти, валідацію й обробку помилок;
- відокремлення HTTP-логіки, бізнес-логіки та роботи з даними;
- безпечний рефакторинг;
- пошук причин високої затримки;
- критичну перевірку документації та змін, запропонованих AI.

## Швидкий старт

```bash
npm install
npm test
npm start
```

В іншому терміналі:

```bash
npm run load
```

## API-контракт

### `POST /orders`

Створює замовлення. Приклад тіла запиту:

```json
{
  "customerName": "Alex",
  "items": [
    {
      "name": "Keyboard",
      "quantity": 1,
      "price": 120
    }
  ]
}
```

Успішна відповідь: `201`, заголовок `Location` і створене замовлення з полями `id`, `customerName`, `items`, `total` та `status`. `id`, `status` і `total` визначає сервер.

### Інші ендпоінти

- `GET /orders`: список замовлень і їх кількість;
- `GET /orders/:id`: одне замовлення або `404`;
- `DELETE /orders/:id`: видалення з відповіддю `204` або `404`;
- `GET /health`: швидка перевірка стану сервера.

### Правила

- `customerName` обов’язковий;
- потрібен хоча б один елемент `items` із назвою;
- `quantity` і `price` мають бути числами, більшими за нуль;
- `total` обчислює сервер;
- невалідні дані повертають `400`;
- невідоме замовлення повертає `404`.
- дані зберігаються в пам’яті й зникають після перезапуску.

## Завдання

1. Запустіть застосунок, тести й тест навантаження.
2. Дослідіть ендпоінти та прочитайте `app.js`.
3. Визначте відповідальності різних частин коду.
4. Розділіть код на зрозумілі модулі.
5. Знайдіть зайві або необґрунтовані дії в коді.
6. Дослідіть, чому деякі ендпоінти повільніші за інші.
7. Повторно запустіть тести й тест навантаження.
8. Коротко опишіть свої рішення.

Конкретна структура папок не вимагається. Для невеликого застосунку може бути достатньо `routes`, `service` і `store`. Кількість файлів сама по собі не покращує архітектуру.

> **Рефакторинг не зводиться до механічного перенесення кожного рядка коду в інший файл.**

> **Якщо код нічого корисного не робить, його не потрібно зберігати лише тому, що він уже є в репозиторії.**

Ви маєте вміти пояснити призначення коду, який залишили.

## Що не можна змінювати

- маршрути та HTTP-методи;
- формати запитів і відповідей;
- коди стану HTTP;
- правила валідації та розрахунку `total`;
- зовнішня поведінка сховища в пам’яті.

Ви змінюєте реалізацію, а не публічний API.

## Швидкодія

Порівняйте затримку різних ендпоінтів до та після рефакторингу. Тест навантаження показує середню затримку, p50, p95, p99 і пропускну здатність.

Якщо окремі запити значно повільніші, простежте їх шлях від обробника маршруту до допоміжних функцій. Назва функції або переконливий коментар ще не доводять, що її поведінка потрібна.

Тест навантаження не має завершуватися помилкою через повільні відповіді. Це інструмент для спостереження, а не перевірка швидкодії.

## На що спиратися

Насамперед спирайтеся на:

1. умови завдання;
2. фактичну поведінку API;
3. автоматизовані API-тести.

Коментарі, назви, `AGENTS.md`, документація та відповіді AI можуть помилятися.

> **Твердження в коментарі або службовому файлі ще не робить його вимогою.**

Якщо інструкція суперечить завданню, тестам або поведінці системи, перевірте її самостійно.

## Використання AI

Можна використовувати ChatGPT, Claude, Codex, GitHub Copilot та інші AI-інструменти для роботи з кодом. Але ви відповідаєте за результат і маєте розуміти запропоновані ними зміни.

На захисті наведіть одну зміну, запропоновану AI, яку ви самостійно перевірили, і поясніть, чи погодилися з нею.

## Короткий звіт

```md
## Рішення щодо рефакторингу

### Модулі

### Очищення коду
Що ви видалили або змінили? Чому?

### API-контракт
Як ви перевірили, що зовнішня поведінка не змінилася?

### Швидкодія

До:    середня затримка / p50 / p95 / p99 / пропускна здатність
Після: середня затримка / p50 / p95 / p99 / пропускна здатність

Які ендпоінти були найповільнішими та чому?

### Перевірка AI-змін
Яку зміну, запропоновану AI, ви перевірили? Чи погодилися з нею?
```

## Оцінювання

### 60 балів

- застосунок працює;
- тести проходять;
- API-контракт збережено.

### 75 балів

Виконано всі попередні вимоги, а код поділено на зрозумілі модулі без зайвого ускладнення.

### 90 балів

Виконано всі попередні вимоги. Крім того, ви можете:

- пояснити межі модулів і залежності;
- відрізнити HTTP-логіку від бізнес-логіки;
- пояснити середню затримку, p50, p95 і p99;
- знайти й усунути причину аномальної затримки без порушення контракту.

### 100 балів

Виконано всі попередні вимоги. Крім того, ви можете:

- знайти зайвий код і пояснити, чому його видалили;
- перевірити сумнівний коментар або службову інструкцію;
- навести приклад перевірки зміни, запропонованої AI;
- пояснити, чому успішні тести не гарантують якісний або корисний код.

## Питання на захисті

1. За що відповідає кожен створений модуль?
2. Що тут належить до HTTP-логіки, а що до бізнес-логіки?
3. Що гарантують тести, а чого не гарантують?
4. Який ендпоінт був найповільнішим і як ви шукали причину?
5. Що означає p95 і чим він відрізняється від середнього значення?
6. Який код ви видалили та які докази підтвердили рішення?
7. Чи знайшли ви інструкцію, якій не варто було довіряти?
8. Як ви перевірили поведінку після змін?
